## SWAAG — one user-facing manager, many independently supervised workers

**User problem:** keeping multiple useful autonomous agents working on long tasks without supervising each process, repeating instructions, losing background results or being unable to ask for progress or change direction. The user wants one conversation with a *team leader* while workers continue, scheduled according to task dependencies, backend/model capacity, shared resources and user priorities.

**Architecture and intended result:** an always-queryable orchestrator/front-end boundary separate from long-lived workers; independent, durable worker status, progress, questions and typed user controls; scheduling of parallel/dependent worker plans across configured models; event-sourced complete original history and on-demand, budget-aware context construction; notes, reusable knowledge and authorized unattended follow-up work as independent supporting capabilities. Chat/voice are interfaces to the same central orchestrator, not separate authority for creating workers. These capabilities are real source-backed implementation areas, with the usual limitations from model quality, configured tools and external integrations.

**Critical current state:** `communication.idle_work_mode` defaults to `finish_only`, not perpetual autonomous production. `authorized_backlog` and `autonomous_continue` are optional modes with permission, queue and resource gates. Complete history/notes infrastructure exists but automatic note-taking and historical analysis across all projects are not proven always-on services. The website cannot imply 24/7 autonomy is enabled by default or that subjective worker task quality is guaranteed.

**Current alternatives:** Codex and Claude Code already support capable coding agents, tools, delegated workers, persistent session data and extensibility. OpenAI Dots also supports one human-facing personal agent with background agents in parallel across conversations; SWAAG is **not the only** assistant with this interaction. SWAAG's narrower design emphasis is a *self-operated, inspectable and configurable agent runtime* where a developer owns local model choices, the orchestrator/worker interfaces, model slot scheduling, event history and background policy. This is an architectural distinction and potentially valuable fit for customers who need that control; a formal apples-to-apples reliability/speed benchmark, commercial advantage and customer value remain unproven. Earlier qualitative assessments favoring SWAAG's organization under certain constraints are not a reproducible modern Codex/Claude/Dots benchmark and must never be presented as a measured leaderboard.

Public source/evidence: `https://github.com/HansPeterRadtke/swaag`, its README, `docs/design-principles.md`, `docs/questions-and-background-work.md`, `docs/supervision-and-progress.md` and tests. Competitive official documentation: `https://learn.chatgpt.com/docs/agent-configuration/subagents`, `https://learn.chatgpt.com/docs/dots`, `https://claude.com/resources/articles/subagents-in-claude-code`. ## KnowMoreDiRT — scientific discourse reasoning over chaotically organized knowledge

**User problem:** organizations accumulate badly named, irregularly nested folders filled with years of unstructured text, reports, logs, tables and changing records. Even if search retrieves a matching passage, it may not answer the real question: two identical-looking laws differ by one digit/date; an alleged fact is only a quote; another chunk reveals an entire account was a child's dream; two names may refer to different entities. The system must locate relevant evidence *and* carry its governing meaning, authority and context to the answer.

**DRT-based architecture:** native filesystem metadata catalog; exact source-linked raw text chunks; sentence/passage embeddings for approximate semantic candidate search without an LLM serially comparing every database entry; DRT/DRS formal discourse referents, predicates, truth conditions, scope, identity, negation, temporal relationships and nested reports; engineering DSPG graph/database for queryable source provenance and multi-passage relationships. It keeps sources authoritative, may say 'unknown' when the corpus fails to establish a fact, and aspires to scale meaning-based search without requiring manual schema/manifest preparation.

**Scientific accuracy:** formal Discourse Representation Theory was introduced by Hans Kamp in the early 1980s, drawing on a much longer tradition of philosophical logic and linguistic semantics; DRT itself is **not centuries old**. See Stanford Encyclopedia of Philosophy `https://plato.stanford.edu/entries/discourse-representation-theory/`. Vector search is an efficient candidate-retrieval mechanism, not a proof of logical implication; DRT structures represent meaning, not an automatic correctness guarantee.

**Current implementation vs aspiration:** a raw *readable-text* folder, `initialize(folder_path)` then `question(text) -> string`; the public API does not return full citations with each answer. Model-backed DRS/query integration required in normal runtime; an experimental one-file source-backed answer and source-revision case exists, not an enterprise benchmark. Separate native KMD FileDB has operated on Raspi's library metadata; that does not establish a finished semantic reasoning system across every original PDF. Current `docs/evaluation.md` contains historical/conditional regression results, which must not be conflated with live fresh model success. Independent long-horizon, cold-query, multi-source, adversarial and throughput comparisons remain open.

**Current alternatives:** Codex/Claude Code perform document search; Microsoft GraphRAG extracts entities, relationships, claims and vector representations, and LlamaIndex supports property graph/vector retrieval. KMD's specific research angle is combining **schema-free raw-folder sources, native filesystem metadata, source provenance and DRT-style dynamic truth/scope representation**, rather than just a generic graph database. It is not yet shown to be more accurate or faster than those alternatives on the same corpus. Relevant sources: `https://github.com/HansPeterRadtke/KnowMoreDiRT`, `docs/theory.md`, `docs/architecture.md`, `docs/public_api.md`, `docs/evaluation.md`; `https://microsoft.github.io/graphrag/index/overview/`; `https://developers.llamaindex.ai/python/framework/module_guides/indexing/index_guide/`.
